# Port the Markdown Editor from Electron to Tauri

## Context

The editor ships as an Electron 40 app. The goal is the same app on Tauri 2, built inside `tauri/` (a copy of the relevant files): same UI, same features, same general code organization, and a test suite that tests the same things. All reading and writing stayed inside `tauri/` and `.claude/` until Phase 11 moved the app to the repository root (its Rust source in `src/tauri/`, `Cargo.toml` and `tauri.conf.json` at the root, Cargo's output in `target/`) and removed the Electron app.

## What the code establishes

1. The frontend is plain ES modules with no bundler. `src/web/index.html` loads `scripts/app.js`; web modules import the parser through paths that climb to `src/` (`../../../parsers/old/...`). The page must be served from a root that holds `web/` and `parsers/old/` side by side, with the page at `web/index.html`.
2. The renderer reaches Electron only through `window.electronAPI`, built by the bridge script in `src/electron`. The main process reaches the renderer through `menu:action` and `api:external` messages and through `executeJavaScript` calls on `window.editorAPI`, `window.__flushOpenFiles` and `window.__editorFilePath`.
3. Renderer behaviour that depends on Electron beyond `electronAPI`:
   - Image sources become `file://` URLs (`WritingRenderer.resolveImageSrc`, three `img.src` assignments at `renderers/writing/index.js:791,1147,1270`), and the image modal preview assigns raw paths (`image-modal.js:179`). This works only because the page is a `file://` page with `webSecurity: false`.
   - `utility/export/html-export.js` strips that `file://` prefix off again when exporting.
   - Dropped files are turned into paths with `webUtils.getPathForFile` (`handlers/event-handler.js:285,308`).
   - `document.title` (set in `Editor.updateWindowTitle`) becomes the window title automatically.
   - The Edit menu's Cut, Copy, Paste and Select All use Electron roles; the right-click menu (Copy, Cut, Paste, Inspect Element) comes from the main process.
   - The renderer handles Ctrl+Z, Ctrl+Y and Ctrl+A itself and calls `preventDefault`, which is what keeps Electron's menu accelerators from firing a second time.
   - `KeyboardHandler` listens on `document` in both views for 21 shortcuts, among them Ctrl+F, Ctrl+Shift+I and Ctrl+Shift+C, which WebView2 by default keeps for its own find bar and DevTools.
   - `table-modal.js:107` calls `window.confirm` when shrinking a table would drop data. Electron shows page dialogs as native message boxes; WebView2 shows its own browser-styled dialog.
4. Main-process features to carry over: window sizing (800 x round(800 x sqrt 2), minimum 600 x 848), bounds saved as work-area ratios with maximized state, show after ready, CLI file argument, session save and restore (open files, cursor path, ToC heading path), close flow (flush, unsaved-changes prompt), `STARTUP_TIMING`, `--max-old-space-size=0`, TESTING behaviour, the full menu (File, Edit, View, Help, Open Recent, open-file checkboxes, Copy File Path enabled state), Gather Images, Reload, Debug, About, context menu, file dialogs, HTML export with `default.css` and reveal in folder, image browse and rename, relative image paths, settings in SQLite, the scripting API registry.
5. The unsaved-changes prompt is a message box with four buttons (Save, Save As..., Discard, Cancel). `tauri-plugin-dialog` supports at most three.
6. Tests:
   - 14 unit tests (`node --test`) on the parser, editor helpers and modals; none touch Electron or the writing renderer. (`jsdom` is used only by `src/parsers/new`'s own spec runner.)
   - 64 Playwright specs. 6 of them load the web app in Playwright Firefox through `test/integration/test-http-server.js` (`cursor-scroll`, `range-handling`, `heading-input`, `page-height`, `toc-scroll`, `toc-highlight`). 58 launch the Electron app through `_electron.launch` in `test-utils.js`.
   - 9 of the 58 reach into the main process with `electronApp.evaluate`: `paste` and `list` (clipboard write), `checklist` (stub `dialog.showMessageBox` response), `copy-file-path` (menu item enabled state, menu item click, clipboard read), `editor` (window count), `export-html` (stub `shell.showItemInFolder`, send `menu:action`), `preferences-margins` (send `menu:action`), `reload` (settings set), `session-save` (save open files, settings get, restore open files).
   - Specs also call `window.electronAPI` directly (`reload`, `page-resize`, `style-element-injection`, `style-injection-toc`, `copy-file-path`) and use `window.editorAPI`, `__editor`, `__flushOpenFiles`.
   - `file-buttons`, `reload` and `copy-file-path` read `README.md` from the project root. `tauri/README.md` does not exist.
7. Tooling: `@types/node` currently arrives through the `electron` package (`jsconfig.json` has `types: ["node"]`). `src/parsers/new/node_modules` (holding a Biome binary) sits inside `src/`. `lint-comments.js`, Biome, ESLint and tsc cover `src`, `test` and `scripts`. `scripts/launcher.nsi`, `scripts/generate-api-docs.js`, `.github/` and `docs/api/` are not in `tauri/`; the `docs` npm script points at the missing generator. `scripts/clean-dist.js` is not referenced by any npm script. The `cleanup` and `test:cleanup` scripts use `rm -rf`, which cmd.exe does not provide. `npm run setup` also installs the Playwright Firefox that the 6 Firefox specs need.
8. `scripts\test.bat` is the test procedure for normal work. It is not in `tauri/` and is not part of the port; the port's checks use the commands under Port test commands.
9. `design.md` requires one class per file, JSDoc everywhere, no nested function declarations and no inline function arguments beyond trivial arrows. `lint-comments.js` reports divider comments such as the `// ==========` banners in Electron's bridge script (which it never saw, being a `.cjs` file), but it only prints them: it exits with code 0 even when it finds some, although its file overview says it exits with 1. A passing `lint` therefore does not prove there are none, so its output is read.
10. Every launch-based spec opens its app in `beforeAll`, which runs under the 5 second test timeout locally (`playwright.config.js`).
11. Every text file in `tauri/` outside `node_modules` uses LF already. No saved check enforces that for new files.
12. The app has no dynamic `import()`, so every module loads at startup. Tauri's embedded assets are matched case-sensitively where Electron's `file://` loads on Windows were not, so the first launch (Phase 2 step 15) shows any import whose case differs from the file name.
13. Documents can already run scripts in the editor. `WritingRenderer.applyHtmlAttributes` copies an HTML block's attributes verbatim onto a real element, `srcdoc` included, so `<iframe srcdoc="<script src='https://...'></script>">` becomes a frame that shares the app's origin and inherits the page CSP, whose `script-src 'self' https: http:` lets the remote script load. That script can call `parent.electronAPI`, and `img-src https:` lets it send out what it reads. Raw `<script>` blocks are only hidden by the renderer today; this plan assumes they will run one day. Under Electron, every `electronAPI` member was open to any such script (`contextIsolation` hid only the bridge script's own variables), the bridge script also ran on any remote page the window navigated to and in every `window.open` window, and every permission request was granted.

## Decisions

### Backend (Rust, `src-tauri/src`)

- Each Electron main-process module becomes one Rust module with the same responsibilities and the same method names in snake_case. `restoreOpenFiles` exists twice in Electron (main.js, menu-builder.js); it is written once and called from both places.
- Rust follows the same conventions as the JS: a doc comment on every item, one main type per module, handlers as named functions with closures only for trivial forwarding, no divider comments.
- Concerns Electron handled itself get their own modules rather than growing `main.rs`: `web_contents.rs`, `message_box.rs`, and `webview_settings.rs` (the WebView2 and WebKit settings, browser arguments, script dialog and permission handling, and the accelerator key forwarding of Phase 3 step 11). The Cargo package is named `markdown-editor` (the `tauri init` template would name it `app`), so the executable is `markdown-editor.exe`.
- Pure logic (relative image paths, the Gather Images scan, bounds ratio math, recent-files list, settings serialization, API parameter validation, message box button mapping, menu templates) is written as plain functions so it can have Rust unit tests in each module's `#[cfg(test)]` block. These Rust unit tests are new; the Electron main process had none. They touch no disk: settings tests use an in-memory SQLite database, and file-system questions (exists, size) are passed in as functions. The path tests pin Node's `path` behaviour that the code relied on, including the case-insensitive comparison `path.relative` does on Windows; the Gather Images tests pin `String.replace`'s first-occurrence replacement, the `-2`, `-3` collision names and the same-size reuse; the texts, buttons, `defaultId` and `cancelId` of every message box the backend shows (unsaved changes, About, the three Gather Images boxes) and the titles, filters and default names of every file dialog are built by plain functions and pinned in Rust tests against the Electron code; the Save As tests pin `path.extname` (`name.` counts as having an extension, `.name` does not, so only the latter gets `.md`). Gather Images hands the new text back inside a JS template literal, which turns CRLF and lone CR into LF; the port applies that same change before handing the text back, and a Rust test pins it.
- Files are read and written as UTF-8 the way Node's `utf-8` encoding did: invalid bytes become U+FFFD and a byte order mark stays in the text. Error messages keep their prefixes (`Failed to load file: `, `Failed to save file: `, `Failed to export HTML: `); the operating system's part of the message comes from Rust instead of Node, so its wording differs.
- Each `ipcMain.handle` channel becomes a `#[tauri::command]` named after it (`file:loadPath` becomes `file_load_path`) with the same arguments and result shapes (`{ success, filePath?, message? }`, `{ action }`, `{ response }`, `{ success, files }`, a plain string for `path:toRelative`). Optional fields are omitted rather than sent as `null`, so the renderer's `!== undefined` checks keep working: `settings_get` omits `value` for a missing key and keeps `null` for a stored `null`.
- `web_contents::send(window, channel, action, args)` emits a Tauri event named `menu:action` or `api:external` with payload `{ action, args }`. Tauri's JS `listen` registers asynchronously, so messages and `execute_javascript` calls made before the bridge reports ready for the current page are held in Rust and run once it does; the flag resets on every page load.
- `web_contents::execute_javascript(window, code)` evaluates code in the page, the page posts the resolved value back through an internal command keyed by request id, and the Rust caller awaits it, matching Electron's promise-returning `executeJavaScript`. Strings embedded in code are JSON-encoded. Calls still pending when the page unloads are rejected, as Electron rejected them when the renderer went away, so the close flow's `try`/`catch` path works the same.
- `window.alert` and `window.confirm` go through `message_box.rs` with Electron's presentation (OK, or OK and Cancel): on Windows by turning off WebView2's default script dialogs and handling `ScriptDialogOpening`, on Linux through WebKitGTK's `script-dialog` signal; on macOS wry's own panel is checked against Electron's in Phase 9. In `test-hooks` builds these boxes are recorded and answered from the test's stub like every other message box (see Tests), so no page dialog can block a test or appear on screen; no existing spec relies on Playwright auto-dismissing a page dialog.
- Settings: `rusqlite` with bundled SQLite, the same `settings(key TEXT PRIMARY KEY, value TEXT NOT NULL)` table and the same keys (the backend writes `windowBounds`, `openFiles` and `recentFiles`; the renderer writes the rest), JSON values (a value that does not parse comes back as the raw string, as now), WAL mode, and a 5 second busy timeout, which is `better-sqlite3`'s default and `rusqlite` does not set (several app instances share one database during test runs). File `settings.db` in the Tauri app config directory, created if missing. Settings written by an Electron install are not read.
- Message boxes: `message_box.rs` implements Electron's `showMessageBox` contract (type, title, message, detail, buttons, defaultId, cancelId, returns the button index) the way Electron renders it per platform: Windows `TaskDialogIndirect` with Electron's mapping (labels like OK, Yes, No, Cancel become common buttons, other labels become command links, message as main instruction when there is a detail), macOS `NSAlert` as a window sheet, Linux `GtkMessageDialog`. Closing the box without a button returns `cancelId`, as in Electron. The label-to-button mapping is a plain function with Rust tests. `TaskDialogIndirect` needs Common Controls 6 in the application manifest; if Tauri's default Windows manifest lacks it, `build.rs` supplies one that has it. Platform crates (`windows`, `webview2-com`, `objc2-app-kit`, `webkit2gtk`) sit in `[target.'cfg(...)'.dependencies]` sections. File dialogs use `tauri-plugin-dialog` with the same titles, filters and default names, parented to the window.
- Commands return errors as values or rejected promises, as the Electron handlers did; nothing in a command path panics on user data.
- Threads: menu events arrive on the main thread, and a blocking dialog there would deadlock Tauri's event loop, so menu handlers that open dialogs (Load, Gather Images, About) hand the work to an async task. The Windows task dialog runs on its own thread with the window as owner, as Electron's asynchronous message box did; `NSAlert` runs on the main thread, with its result passed back over a channel. No lock on shared state (file manager, menu builder, settings) is held across an `await`.
- Other Electron APIs: `clipboard` becomes `tauri-plugin-clipboard-manager`; `shell.showItemInFolder` and `shell.openExternal` become `tauri-plugin-opener`; `app.getVersion` reads the package info (the `version` in `tauri.conf.json` points at `../package.json`); DevTools use Tauri's `devtools` feature. Help > Debug and Inspect Element open DevTools; selecting the element under the cursor is not available through Tauri's webview API.
- The window is created in `main.rs` (the generated window entry in `tauri.conf.json` is removed), so its size and position can come from the settings first, as in `createWindow`.
- Window (`main.rs`): the Electron sizes are outer sizes, so the Tauri window is sized by its outer frame, the minimum size included (Tauri sets inner sizes, so the frame's size is added); bounds are stored in the same format (DIPs, ratios of the work area of the display with the largest overlap); the non-maximized bounds are tracked so a maximized window still saves its restore bounds; with no saved position the operating system places the window, as before; the window is shown after the first page load; CLI file argument, session restore, close flow, `STARTUP_TIMING` and macOS reopen behave as in `main.js`. The CLI file load and the first show each happen once, on the first page load, as Electron's `once` handlers did. WebView2 gets `--js-flags=--max-old-space-size=0` in addition to Tauri's default arguments; WebKit on macOS and Linux has no such switch and manages its own heap. WebView2 also gets `--lang=en-US`: the Electron build ships only the `en-US` locale (`electronLanguages`), so its built-in UI, form validation messages and default `Intl` locale are English on every system, and `WordCountModal` formats counts with `toLocaleString()` (`1,234`, where a WebView2 following a Dutch or German Windows would print `1.234`). Chromium honours only the last `--disable-features` switch, so Tauri's default list and any feature this plan or the test build turns off are merged into one switch.
- `app_reload` returns its result before the page starts reloading, as Electron's `reloadIgnoringCache` did, so `reload.spec.js`'s `evaluate` resolves before its page goes away. On Windows the reload bypasses the cache (DevTools protocol `Page.reload` with `ignoreCache`), matching `reloadIgnoringCache`.
- `TESTING=1` keeps its Electron meaning: the window never appears on screen, open files are not restored automatically, and closing saves the window bounds and then destroys the window at once.
- WebView2 settings that would otherwise differ from Electron: status bar off (no URL bubble on link hover), browser accelerator keys off (find, print, reload, save page, new window, back and forward, DevTools keys, none of which Electron has without menu roles), zoom off (Electron only raises a `zoom-changed` event on Ctrl+wheel and has no zoom keys without menu roles), pinch zoom off (Electron disables visual zoom), built-in context menu off, swipe navigation off, general autofill and password autosave off.
- Electron web preferences that `main.js` leaves at their defaults, and that WebView2 does not share, are matched as well, since documents can embed media and iframes: autoplay without a user gesture (Electron's `autoplayPolicy` default, WebView2 argument `--autoplay-policy=no-user-gesture-required`); and tracking prevention off (Electron has none). Fullscreen is not matched: on the user's instruction (2026-11-17), a fullscreen request does nothing, so the page is served with `Permissions-Policy: fullscreen=()`. Embedded PDFs and generic `monospace` text are checked against Electron in Phase 9, since Electron's `plugins` and `defaultFontFamily` defaults may differ from WebView2's. Permission requests are the exception to matching Electron's defaults; see Security.
- The Windows build links the C runtime statically (`+crt-static` in `src-tauri/.cargo/config.toml`). A Rust MSVC binary otherwise needs `vcruntime140.dll` from the Visual C++ redistributable, which a clean Windows does not have, and the Electron executable needed nothing installed.

### Bridge (`src-tauri/src/backend-bridge.js`)

- Injected with `initialization_script`, so it runs before page scripts on every load, in the main frame only, as Electron's bridge script did, and only on the app's own origin. It uses `window.__TAURI_INTERNALS__`, which Tauri defines before any initialization script; `withGlobalTauri` stays off (see Security). The media protocol's origin for the current platform is written into the script by Rust.
- Defines `window.electronAPI` (read-only, like `contextBridge`) with the same members, arguments and return shapes as Electron's bridge script, plus `toDisplayUrl(url)` and `fromDisplayUrl(url)`. The name stays because renderer modules and specs use it.
- Subscribes to `menu:action` and `api:external` at injection time, tells the backend it is ready once both subscriptions are registered, and queues messages until the renderer registers its callback. Electron dropped messages that arrived before `ipcRenderer.on`; queueing makes CLI loads and session restores deterministic. This is a behaviour difference.
- Mirrors `document.title` into the window title.
- Turns Tauri's native drag-drop event into a DOM `drop` event at the drop point (Tauri reports physical pixels; the bridge converts to CSS pixels), carrying `File` objects whose paths `getPathForFile` returns, so `EventHandler.handleDrop` stays unchanged. A drop the page does not handle (for example in source view, where `handleDrop` returns early) does nothing, as under Electron, whose `navigateOnDragDrop` web preference defaults to off. Tauri's native drop target accepts drags over the whole window, so the copy cursor shows everywhere, not only over the editor; this is a visible difference.
- On a `contextmenu` event the page did not prevent, asks the backend to show the Electron context menu (Copy, Cut, Paste, separator, Inspect Element) at the pointer.

### Renderer seams (the only web code changes)

- `index.html` CSP: add `connect-src 'self' ipc: http://ipc.localhost`; add `media: http://media.localhost` to `img-src`; add `media-src 'self' media: http://media.localhost` (there is no `media-src` today, so media falls back to `default-src 'self'`, which on Electron's `file://` page covered `file://` media).
- `WritingRenderer`: the three `img.src = this.resolveImageSrc(...)` assignments pass the URL through `window.electronAPI?.toDisplayUrl`, falling back to the URL itself (the pattern `event-handler.js` already uses for `getPathForFile`), so the Firefox specs, which have no `electronAPI`, see no change. `resolveImageSrc` stays as it is.
- `ImageModal.updatePreview`: the same treatment for the preview `src`.
- `toDisplayUrl` turns a `file://` URL (percent-decoded to a path), a Windows drive path (`C:\...` or `C:/...`; `resolveImageSrc`'s scheme test lets these through as if `C:` were a scheme, and Electron loaded them relative to its `file://` page) or an absolute POSIX path into a `media` protocol URL (`http://media.localhost/<encoded path>` on Windows, `media://localhost/<encoded path>` elsewhere), and returns every other value unchanged. It records each conversion, and `fromDisplayUrl` returns the recorded original, or its input when there is none.
- `WritingRenderer.applyHtmlAttributes`, which copies an HTML block's attributes verbatim onto real elements, passes `src` and `poster` on `<video>` and `<audio>` through `toDisplayUrl` the same way. Under Electron a `file://` source on those loaded through `webSecurity: false`; without this they would stop loading. `<iframe>` and `<object>` sources are deliberately not converted (see Security), so a `file://` iframe or object that loaded under Electron no longer does; that is a known difference. Relative sources stay as they are, since under Electron they resolved against the page and did not load either. No spec covers these elements, so this is a Phase 9 item.
- `renderHtmlBlock` adds the `sandbox` attribute to same-origin `<iframe>` elements as described under Security.
- `html-export.js` `restoreRelativeImageSources`: maps each image `src`, and the `<video>` and `<audio>` `src` and `poster` attributes, through `fromDisplayUrl` first, so exported HTML matches Electron's output exactly. Exported iframes carry the added `sandbox` attribute; that is a difference in the exported HTML for those frames.
- `url(file:///...)` inside a document's own `<style>` block (with style elements enabled) is not converted and no longer loads; Electron loaded it. This is a known difference.
- Two renderer comments become false and are updated with the seams: `event-handler.js:307` ("the Electron webUtils bridge") and `image-helper.js:31` ("the main process which uses Node's `path` module").
- Tauri's asset protocol stays off; local files come through the `media` protocol (see Security). Tauri's own CSP injection stays off (`csp: null`), so the page's meta tag remains the policy, as in Electron.

### Security

Threat model: every document is untrusted input, and its scripts are assumed to run in the editor page, today through same-origin frames (fact 13) and in future through script support. Nothing in the port may rely on "document scripts do not run". Anything a script in the page can reach counts as reachable by a document.

What a page script can reach through the bridge, carried over from Electron unchanged because the renderer and specs use it: read any file (`loadFilePath`); make any path the save target (`notifyOpenFiles` sets the backend's current file) and write it (`saveFile`); write `<name>.html` and overwrite `default.css` in that folder (`exportHtml`); rename any file (`renameImage`); queue arbitrary files for the next start (`setSetting('openFiles', ...)`).

Decisions:

- The boundary sits where Tauri enforces it, in capabilities and in the commands' own checks. Tauri cannot hide its IPC from scripts in the page: `window.__TAURI_INTERNALS__` is always defined, and same-origin frames reach it through `parent`.
- Capabilities grant the `main` window, for the app's own origin only (plus the dev server's origin in dev builds), exactly these: event listen and unlisten, window set-title, and the app's own commands, through an app manifest in `build.rs` so that app commands are not allowed by default. There is no `core:default`, which would add event emit, window, webview, menu, path, app and other permissions. There are no plugin permissions at all, because the dialog, clipboard and opener plugins are called from Rust only. In particular there is no `opener` permission, which would let a page open files and launch programs; whatever `tauri init` puts in the capability file is replaced.
- `withGlobalTauri` stays off. The bridge calls `window.__TAURI_INTERNALS__` directly (invoke, the event plugin's listen and unlisten commands), so the page's globals are the ones Electron gave it: `electronAPI` and `editorAPI`. This is tidiness, not a boundary.
- The bridge installs itself only when the page's origin is the app's own.
- Main-frame navigation is limited to the app's own pages (and the dev server in dev). Under Electron a link or form inside an embedded frame could, after a click, replace the editor with a remote page that then had `electronAPI`.
- A new-window request (`window.open`, `target=_blank` in embedded content) never opens an app window. `http:` and `https:` URLs go to the system browser through the opener plugin, called from Rust; everything else is refused. Electron opened an in-app window and ran its bridge script in it. This is a behaviour difference.
- Permission requests (camera, microphone, location, notifications, clipboard read and the like) are denied without a prompt. Electron granted them all; under this threat model that would give a document's scripts the camera. This is a behaviour difference.
- Local files reach the page only through the app's own `media` protocol (`media_protocol.rs`), not Tauri's asset protocol, which stays off. It serves files with image, audio and video extensions only. Every response carries the right `Content-Type`, `X-Content-Type-Options: nosniff` and `Content-Security-Policy: sandbox`, so a framed SVG or any other served file cannot run script. It answers byte-range requests, so media can seek. It sends no CORS headers, so a page script cannot read the pixels or bytes. Tauri's asset protocol with scope `**` would let a framed local HTML or SVG file fetch every other file on disk. The cost: an image file without a known image extension no longer loads, where Electron loaded any file.
- The `applyHtmlAttributes` seam converts `src` and `poster` on `<video>` and `<audio>` only. `<iframe>` and `<object>` sources are left as written, so a document cannot frame a local file.
- An `<iframe>` that a document creates with same-origin content gets a `sandbox` attribute without `allow-same-origin`. Same-origin content means `srcdoc`, or a `src` that is relative, `about:`, `blob:` or on the app's origin. The frame keeps any other sandbox tokens the document gave, or gets `allow-scripts allow-forms allow-popups` when it gave none. Its scripts then run in an opaque origin and cannot reach `parent.electronAPI`. Cross-origin `http:` and `https:` iframes stay as written: their origin already isolates them, and the navigation limit stops them taking over the window. This is a renderer change outside the seams, added, not asked for, because the `srcdoc` path is a live script path today. It is a behaviour difference only for framed content that reached into the editor.
- Commands that trust a path from the renderer keep Electron's behaviour, because specs depend on it: `copy-file-path.spec.js` hands `notifyOpenFiles` a path the backend never issued. The one narrowing is that `image_rename` refuses a new name that is not a plain file name (path separators, `..`); the image dialog's rename field never produces one.
- The CSP stays as it is, plus the IPC and media sources. Its `script-src https: http:` is what the `srcdoc` path uses, and with the sandbox above it no longer reaches the bridge.
- Test-only surfaces never reach release builds: the stdin hooks and the DevTools port exist only with the `test-hooks` feature. DevTools in release open only from F12 or the Help menu, as in Electron.
- `npm start`'s dev server listens on every interface, as the Firefox specs' server does, so while it runs `src/` can be read from the local network.
- Tauri's isolation pattern is not used. It can check IPC payloads, but it cannot tell the bridge's calls from a document script's, so it adds nothing here over capabilities and command checks.
- Before document scripts may run on purpose, the documentation (Phase 8) lists what has to change first: the renderer-trusted paths above must become paths the backend issued (dialogs, CLI argument, recent files, drops, restore), with `copy-file-path.spec.js` changing to match; document content has to render in a sandboxed frame that has no bridge; and `script-src` must drop `https:` and `http:`.

### Menus

- Same template, labels, order, submenus, separators, enabled and checked states, rebuilt on the same triggers. As in Electron, `menu_builder.rs` first builds the template as data (`build_file_menu` and the rest return item descriptions) and then turns it into Tauri menu items, so Rust tests can compare the template item by item with the Electron one (labels, order, accelerators, enabled states, Open Recent and View contents for given inputs), and the context menu likewise.
- Accelerators follow Electron's order: on Windows and Linux the page sees a key first and the menu acts only on keys the page did not handle; on macOS the menu takes key equivalents first. The six Edit shortcuts the page handles itself (Ctrl+Z, Ctrl+Y, Ctrl+X, Ctrl+C, Ctrl+V, Ctrl+A) therefore must not be registered on Windows or Linux, or they would fire twice or bypass the editor. All other menu shortcuts are registered on every platform.
- Edit items per platform, each matching what Electron's item did:

| Item | Windows | macOS | Linux |
|---|---|---|---|
| Undo, Redo | custom item sending `edit:undo` / `edit:redo`; shortcut written after a tab in the item text (Win32 shows it right-aligned like an accelerator), not registered | same, with registered Cmd+Z / Cmd+Y | same, without shortcut text (GTK gives registered accelerators priority over the webview, and cannot show text without registering) |
| Cut, Copy, Paste | custom item, shortcut text after a tab; a click sends that keystroke to the focused webview, which runs the native clipboard command exactly as a key press does under Electron | Tauri predefined item (native selector, like Electron's role) | custom item without shortcut text running WebKitGTK's editing command |
| Select All | custom item, shortcut text after a tab; a click runs `document.execCommand('selectAll')` (Electron's role selected natively; it did not run the editor's Ctrl+A cycle) | Tauri predefined item | custom item without shortcut text running WebKitGTK's select-all command |

- The context menu's Copy, Cut and Paste use the same per-platform implementation as the Edit items, as both were Electron roles.
- Known difference on Windows: because Cut, Copy and Paste clicks reach the page as key presses, the editor sees a keydown for them, which Electron's roles did not produce. Its only effect is the one any key press has, such as ending a Ctrl+A selection cycle. WebView2 offers no way to run an editing command without a key event.
- On Linux, muda may treat `_` and `&` in labels as mnemonic markers; Open Recent labels are full paths, so a path containing either is a Phase 9 check.
- On macOS the first submenu of the menu bar becomes the application menu, in Electron and in Tauri alike, so File's items appear under the app name there, as now.
- None of `KeyboardHandler`'s 21 shortcuts is a menu accelerator, so no menu accelerator can take a key the page owns on Linux or macOS either.

## Phases

### Phase 0: working rules

- Before each edit of an existing file, a copy goes to `.claude/snapshots/`, named after the file's path relative to the repository root (slashes as `__`) plus a `YYYYMMDD-HHMMSS` suffix (with a counter if two land in the same second), so snapshots never overwrite each other. Existing files are changed with Edit; Write is only for new files.
- Every written file uses LF; no em dashes; no banner comments; JS keeps JSDoc, backtick strings and `design.md`'s rules (one class per file, no nested function declarations, no inline function arguments beyond trivial arrows).
- Shell commands go through the Bash tool as `cmd //c ...`; no PowerShell, python, sed, perl, awk or heredoc.
- Checks use only the commands under Port test commands, each run on the named test the step gives; a step never runs the whole suite to verify itself. `scripts\test.bat` is not used. Cargo runs only inside npm scripts.
- Test first. A test that a step adds is run before the code it tests exists, and must fail for the reason the step is about (a missing hook, command, value or behaviour), not for an unrelated one. Then the code is written and the same command must pass. An existing spec that a step is meant to make pass is run at the start of the step, and its failure noted. Next to the step's box, the plan file records the failing run and the passing run (command and outcome).
- Steps run one at a time, in order. A step is done, and its box in the checklist at the end ticked, only when its check passes; the next step starts only after that. If the check cannot be made to pass, stop and report it. If a step turns out bigger than its description, stop and say so instead of carrying on.
- Only appearance, meaning pixels (how the task dialog, the menu bar and the fonts look), is left to the user in Phase 9. Behaviour, texts, options, settings and state are checked by tests, through the test hooks where the page cannot see them. Two things need a person: real keyboard routing through the operating system (step 3.11), and anything that shows a window on screen, which waits for the user's yes.
- From Phase 2 on, every step that changes JS, CSS or Rust also ends with `npm run lint` passing. The one exception is steps 2.7 to 2.11: `launchApp` changes shape in 2.7 and the specs that call it are converted across 2.8 to 2.12, so `lint:typing` reports the not-yet-converted folders until 2.12.
- No git commands unless agreed.
- Files outside the repository are written only by tools doing their normal job: the npm, cargo and Playwright caches, and the app's data folder when the user runs it. The Tauri test runs keep their data under `test-results/`.
- The project path contains a space (`markdown editor`), so every script and command quotes its paths.
- The destructive actions this plan agrees to, and no others: deleting the generated `src-tauri/src/lib.rs` (Phase 2), deleting `src/electron/` (Phase 6), `stage-frontend.js` clearing its own `build/frontend/` before copying, and the export and Gather Images specs removing the files they wrote; and in Phase 11, on the user's instruction: removing the old Electron app and the items 11.1 names (11.2), removing `tauri/` once it is empty (11.3), `scripts/build-leftovers.js` removing `build/`, `gen/` and `permissions/` after every build and Rust test run, and removing the scripting API (11.7).
